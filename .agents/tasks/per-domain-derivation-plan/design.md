# Design — Per-Domain SDTM and Per-Dataset ADaM Derivation Plans

## Overview

Today SDTM and ADaM each own exactly one Derivation Plan per workbench aggregate. A single `sdtm_derivation_plan_revisions` row (keyed by `aggregate_id`) carries one typed DAG that spans every domain in the Specification; `adam_derivation_plan_revisions` does the same across every ADaM dataset. The Specification stays a single aggregate holding all domains/datasets, and the plan is aligned to one Specification revision plus one external input-selection revision (Raw for SDTM, SDTM for ADaM). Output coverage is enforced globally in `lower_plan` as a _subset_ check (`required <= writes`).

This change makes the plan **one per domain (SDTM)** and **one per dataset (ADaM)**, while the Specification remains a single all-domains/all-datasets aggregate that the user treats as "the standard." Each per-domain/per-dataset plan is aligned to one Specification revision but covers only its own domain's/dataset's derived targets; collectively the set of plans covers the whole Specification. Each plan is independently versioned with the existing optimistic-concurrency, If-Match, atomic-replacement model. Because plans are now physically separate, a plan can no longer rely on in-graph edges to reach another domain's/dataset's data, so SDTM gains an `sdtm_read` node (ADaM already has `sdtm_read`/`adam_read` nodes but their cross-dataset resolution must change). The SDTM read binding is resolved **from the single Specification aggregate** against the same Specification revision the plan is already aligned to — it introduces no new external input pin.

The decisive technical risk is a **cross-domain/cross-dataset staleness correctness gap**: under a Specification-only binding, domain A's plan reads domain B's output, but a change to B's _plan_ (not the Specification) is invisible to A because only the Specification is pinned. The analysis below (§6) confirms the gap is real and cannot be closed by the Specification-only model alone, and proposes the minimal mechanism to close it: a per-plan set of server-resolved pinned **upstream plan revisions** derived from the read nodes, validated at write time and used as additional staleness edges. This keeps the Raw/SDTM `input_selection_revision` as the only _external_ input pin exactly as the four approved decisions require, while making cross-plan reads correct.

The stack is locked and unchanged: Python 3.13, FastAPI, Pydantic 2 (`extra="forbid"` strict models), SQLAlchemy 2 ORM, Alembic (single ordered history), PostgreSQL 16 (JSONB payloads with explicit `schema_version`), S3-compatible object storage. No new libraries are introduced.

This is a revision after three design-review iterations. The eleven first-iteration findings are addressed in §12; the six second-iteration findings (two MEDIUM, four NIT) in §13; the twelve third-iteration findings (three HIGH, seven MEDIUM, two NIT) in §14. §14 drove material changes to the staleness-propagation model (§6, now transitive), the `GET /lineage` and all-domain deliverable (Define/cSDRG) rewrites (§3.3), the aCRF plan-node resolution path (§2.5, §7 — the real resolver lives in `sdtm/acrf.py`, not a hypothetical trace service), the aggregate validation / ADaM-input-binding model (§3.3, §3.4), and the lost-update serialization (§6, now an aggregate-row lock).

Coverage rule verified: `writes = {node.domain for domain_write}`, `required = {domain.code for domain in domains if any(var.derived)}`, raises `sdtm_plan_output_coverage_missing` when `not required <= writes` (a **subset** check — it does **not** reject writes for non-derived domains and does **not** enforce one write per domain). ## 2. Persistence shape and natural keys

### 2.1 SDTM

`SdtmDerivationPlanRevision` becomes keyed per domain:

- Add non-null `domain_code: str` (`VARCHAR(8)`, CHECK matching `^[A-Z][A-Z0-9]{1,7}$`, stored uppercase).
- Old `UniqueConstraint("aggregate_id", "revision")` → new `UniqueConstraint("aggregate_id", "domain_code", "revision", name="uq_sdtm_plan_aggregate_domain_revision")`.
- Add index `ix_sdtm_plan_aggregate_domain` on `("aggregate_id", "domain_code")` for "latest plan for this domain."
- `revision` now counts per `(aggregate_id, domain_code)`. One **active** plan per `(aggregate_id, domain_code)` is the max-revision row for that pair (no separate active flag — latest-revision is active, exactly as today per aggregate).
- Add `upstream_plan_pins: JSONB NOT NULL DEFAULT '[]'` storing a sorted, de-duplicated list of `{"domain_code": str, "plan_revision": int}` for every sibling SDTM domain this plan reads via `sdtm_read` (§6). Server-resolved only.

### 2.2 ADaM

`AdamDerivationPlanRevision` becomes keyed per dataset, symmetrically:

- Add non-null `dataset_code: str` (same pattern/length).
- Old `uq_adam_plan_aggregate_revision` → new `UniqueConstraint("aggregate_id", "dataset_code", "revision", name="uq_adam_plan_aggregate_dataset_revision")`.
- Add index `ix_adam_plan_aggregate_dataset` on `("aggregate_id", "dataset_code")`.
- `revision` counts per `(aggregate_id, dataset_code)`.
- Add `upstream_plan_pins: JSONB NOT NULL DEFAULT '[]'` storing `{"dataset_code": str, "plan_revision": int}` for every predecessor dataset read via `adam_read`.

### 2.3 Envelope contract changes (both modules) — scoped reconciliation (Finding 5, 11)

The stored authoring payload gets exactly one new required field and a version bump; no other documented envelope field is adopted in this change.

- `SdtmDerivationPlan` adds required `domain: str` (pattern `^[A-Z][A-Z0-9]{1,7}$`) — the single domain this plan produces.
- `AdamDerivationPlan` adds required `dataset: str` (same pattern) — the single dataset this plan produces.
- `schema_version` field type changes from `Literal["1.0.0"]` to **`Literal["1.1.0"]`** (not a union) on both plan contracts. Adding a required discriminating field is a backward-incompatible payload change; a strict validator must never see a `1.0.0` plan payload after migration, so the `0012` backfill rewrites every stored payload's `schema_version` to `"1.1.0"` and injects `domain`/`dataset` (§2.5). Post-migration no reader encounters a `1.0.0` plan row.

**Response envelope (scoped):** the API `PlanResponse` adds exactly two computed, server-owned fields and keeps the existing `state`:

- `domain` / `dataset` (echoed from the stored payload).
- `alignment_state`: `current | alignment_required`, derived from the row `state` (`aligned→current`, `misaligned→alignment_required`).
- `alignment_reasons`: a list drawn from `specification_changed | input_changed | upstream_plan_changed`, read verbatim from the persisted `alignment_reasons` column (§3.4) — **not** re-derived at read time.

**`alignment_reasons` authoritative invariant (Finding 6 / third-iteration Finding 1).** `alignment_reasons` is persisted as a nullable JSONB column on each plan-revision table and surfaced read-only on the response. The single enforced invariant is: **`alignment_reasons` is empty iff `state == aligned`.** Every write that sets `state` sets `alignment_reasons` in the same statement — a misalign write sets `state="misaligned"` and appends the triggering reason(s); a successful aligned (re-save) write sets `state="aligned"` and clears `alignment_reasons` to `[]`. The response echoes the persisted column verbatim; `alignment_state` is the only field derived from `state` at read time (`aligned→current`, `misaligned→alignment_required`), while `alignment_reasons` is the stored column.

Because the invariant is "`state`/`reasons` are the single source of truth and the response never re-derives staleness," the invariant can only hold if **every** cause of misalignment — including a transitive upstream cause — is written to `state`/`alignment_reasons` the moment it occurs. The third-iteration review (Finding 1) correctly identified that the prior design violated this for the transitive case (A pins B@3, B becomes misaligned without a new revision because its own upstream C changed; A keeps `state=aligned`/`reasons=[]` yet every operation on A fails `409`). The resolution adopted here (§6) makes misalignment propagation **transitive and triggered by any transition into `misaligned`**, so no plan can be effectively unalignable while reporting `aligned` with empty reasons. A repository integration test asserts the iff after every write path, including the transitive chain A→B→C (§10).

The existing `state`, `revision`, `specification_revision`, `input_selection_revision`, `payload`, `fingerprint` fields are retained. The documented-but-unimplemented `module`, `outputs`, `assertions` fields and the "exactly one valid producing output" variable-level rule are **not** introduced here; §9 rewrites §4.7 to describe the _actual_ envelope (`state`/`alignment_state`/`alignment_reasons`/`nodes`/`edges` + per-domain/per-dataset coverage) and records the deferral explicitly so §4.7 no longer diverges on the fields this change touches. `upstream_plan_pins` is surfaced read-only on the response for traceability but is never accepted from a client (rejected by `extra="forbid"`).

Rationale for scoping down rather than fully adopting: adopting `outputs`/`assertions`/`module` and a variable-level single-producer rule is an independently large contract change not authorized by the four approved per-domain decisions. Partially adopting two of six documented fields (the prior design's error) leaves §4.7 still diverging. The scoped choice resolves the divergence for every field this change actually touches and defers the rest with a stated reason.

### 2.4 SDTM read node contract

Add to `src/app/sdtm/contracts.py`:

```python
class SdtmReadNode(StrictModel):
    node_type: Literal["sdtm_read"]
    id: str = Field(min_length=1, max_length=128)
    dataset: str = Field(pattern=r"^[A-Z][A-Z0-9]{1,7}$")  # upstream SDTM domain code
```

Add it to the `SdtmPlanNode` discriminated union. A plan reads its own domain's rows via `raw_read` (unchanged) and reads _other_ produced SDTM domains via `sdtm_read`. The read's binding is the named domain resolved through the Specification (§5), not a new input pin. Field name `dataset` matches the ADaM `SdtmReadNode`/`AdamReadNode` convention so SDTM/ADaM read nodes stay structurally symmetric.

### 2.5 `AcrfPlanNodeLink` and annotation backfill (Finding 7)

**Where plan-node links are actually resolved (third-iteration Finding 4 — correction).** The prior design described a "trace resolver" keyed by `(aggregate, domain_code, plan_revision, node_id)` living in a traceability service. That component does **not** exist, and the correction matters because it changes _which_ code this design must touch. The real resolution of `AcrfPlanNodeLink` lives in **`src/app/sdtm/acrf.py`** in two places, both verified:

- **Link validation on annotation write** (`acrf.py` ~L230): looks up a plan by `select(SdtmDerivationPlanRevision).where(aggregate_id == workbench.id, revision == link.plan_revision)`, then asserts `link.node_id ∈ {node.id for node in plan.nodes}` (`acrf_plan_node_unresolved`).
- **aCRF coverage** (`acrf.py` ~L457/487): loads the aggregate's **max-revision** plan and counts `AcrfPlanNodeLink`s whose `plan_revision != plan_record.revision` as `noncurrent`.
  `kernel/traceability.py`/`trace_links` resolve only aggregate-level entities by `(module, entity_type, entity_id)`; they do not address plan nodes. So the AGENTS.md traceability chain's "SDTM Derivation Plan node" is realized today **only** through these two aCRF paths, not a general trace resolver.

**Why both break under per-domain and the concrete change.** Each domain now has its own `revision` counter, so `(aggregate_id, revision == link.plan_revision)` is **ambiguous** — multiple domains can share revision number 1. Both aCRF sites must therefore key on `(aggregate_id, domain_code, revision)`, which requires `AcrfPlanNodeLink` to carry the domain. Concrete changes:

- Add **optional** `domain: str | None = None` to `AcrfPlanNodeLink` (optional so the strict `extra="forbid"` model does not reject legacy annotation payloads on read; backfilled in `0012` step 3 via the split's `node_id → owning domain_code` map).
- `acrf.py` ~L230 validation: look up the plan by `(aggregate_id, domain_code == link.domain, revision == link.plan_revision)`; a link with `domain is None` after backfill is treated as unresolved and raises the existing `acrf_plan_node_unresolved` (defensive — an orphan whose node did not survive the split).
- `acrf.py` ~L457 coverage: resolve the head plan **per domain** (`aligned_domain_plans` / `latest_plan(..., link.domain)`) and compare each link's `(domain, plan_revision)` against that domain's head, rather than against a single aggregate max-revision plan. The `noncurrent` count becomes "links not pointing at their domain's current head."

This is the full extent of the plan-node resolution change: a **data-shape** change (`+domain` on the link, backfilled) plus a **key** change at the two aCRF sites. No new traceability-service component is introduced. §7 and §10 reflect this (the touch point is `sdtm/acrf.py`, not a trace service, and the test is an aCRF-link resolution test). The reconciliation/`service.py` code that reads `link.get("domain")` for `sdtm_variable` links is a different `target_type` already carrying `domain` and is unaffected.

### 2.6 Migration (`20261009_0012_per_domain_derivation_plans`, down_revision `20261008_0011`) (Finding 8, 11)

One ordered migration, reversible-with-a-guard, applied from an empty DB in tests (no `metadata.create_all`). Steps:

1. `ALTER TABLE sdtm_derivation_plan_revisions ADD COLUMN domain_code VARCHAR(8)` (nullable during backfill), `ADD COLUMN upstream_plan_pins JSONB NOT NULL DEFAULT '[]'`.
2. **Split backfill (deterministic).** For each existing `sdtm_derivation_plan_revisions` row, read its JSONB `payload` (one DAG spanning all domains) and split it into per-domain plans. Implement the split as a **pure dict-to-dict helper inside the migration module** (no app-service import), so the transform is deterministic and testable:
   - Compute `writes = {node.id → node.domain for domain_write}`. The set of produced domains is `written_domains = set(writes.values())`.
   - For a node reachable (over `edges`, following source→target) to the `domain_write` of exactly one domain `D`, assign the node to `D`.
   - **Deterministic multi-consumer ownership rule:** a node reachable to `domain_write`s of two or more domains is **owned by the lexicographically-smallest** written domain among its consumers. Every other consuming domain `D'` receives, in its sub-plan, an `sdtm_read{dataset=<owner domain>}` node plus an edge from that read to the first downstream node `D'` previously consumed from the shared node. The owner's new plan is `revision=1`, so each consuming sub-plan records `upstream_plan_pins=[{"domain_code": <owner>, "plan_revision": 1}]`.
   - **Node-id stability:** node ids are **kept stable** wherever a node lands in exactly one sub-plan. A node that must be _duplicated_ across sub-plans (a shared `raw_read` ancestor, or the shared `raw_read`s feeding several single-consumer sub-DAGs) is **not** given a suffixed id; instead the duplicated copy keeps its original id _within its own sub-plan_ (node ids are unique per plan, and plans are now separate rows, so collision across plans is harmless). This avoids rewriting `AcrfPlanNodeLink.node_id`. The only new ids introduced are the injected `sdtm_read` nodes.
   - **Injected read-node id generation (collision-checked — third-iteration Finding 8).** An injected `sdtm_read` id is generated by **scanning the ids already present in the target sub-plan** and picking the first non-colliding `__read_<owner>_<n>` (n starting at 1). This guards against the (low-probability) case where a legacy author named a real node with the `__read_` prefix: the scan guarantees the injected id is distinct from every id already in that sub-plan. After emitting each sub-plan, the migration **asserts the final per-plan id set is unique** and aborts with context if not (so a malformed emission can never produce a payload that would later fail `SdtmDerivationPlan.valid_graph`'s "plan node IDs must be unique" on first read). A property-test case seeds a legacy node already using the `__read_` prefix and asserts the injected read gets a non-colliding id (§10).
   - For each produced domain emit a per-domain plan row. **Both** the relational `schema_version` column **and** `payload["schema_version"]` are set to `"1.1.0"` on every emitted row (the row stores `schema_version` as a column driven from the payload in `put_plan`, so the two must never diverge after migration): `revision=1`, `domain_code=D`, `state` carried over from the source row, relational `schema_version="1.1.0"`, `payload` = the sub-DAG with `domain=D` injected and `payload["schema_version"]="1.1.0"`, recomputed `fingerprint`, resolved `upstream_plan_pins`, preserved `created_by`/`created_at`.
     - **Shared `created_at` across split rows (third-iteration Finding 12 — intentional).** All per-domain rows split from one legacy row **deliberately inherit the legacy `created_at`/`created_by`** (provenance preservation — the implementer must **not** regenerate `created_at`). The `GET .../derivation-plans` collection orders heads by `(created_at, id)`; among the heads of one split aggregate that share a `created_at`, the order is therefore `id`-determined (UUID order), not authoring order. This is harmless (pagination stays stable because `id` is the unique tie-break — §3.4) and is called out so no one "fixes" it by minting fresh timestamps.
   - Build and persist (in-memory for step 3) a `node_id → owning domain_code` map for annotation backfill.
3. **Annotation backfill.** For each `sdtm_acrf_annotations.links` entry with `target_type == "derivation_plan_node"`, set `domain` from the step-2 `node_id → domain_code` map (matching the link's `plan_revision` lineage to the split). Links whose node did not survive the split keep `domain=null` (defensive, flagged by the resolver).
4. After backfill, `ALTER COLUMN domain_code SET NOT NULL`, drop `uq_sdtm_plan_aggregate_revision`, add `uq_sdtm_plan_aggregate_domain_revision`, add `ix_sdtm_plan_aggregate_domain`.
5. Mirror steps 1–4 for `adam_derivation_plan_revisions` with `dataset_code` grouped by `dataset_write`, `adam_read` → `upstream_plan_pins`, and the same lexicographically-smallest ownership rule for shared nodes feeding multiple `dataset_write`s. ADaM already has `adam_read` nodes, so a shared node feeding two dataset writes becomes an `adam_read{dataset=<owner>}` in the non-owner sub-plan. As in SDTM step 2, every emitted ADaM per-dataset row sets **both** the relational `schema_version` column **and** `payload["schema_version"]` to `"1.1.0"`.
6. **Artifact-staleness consequence (stated explicitly).** Splitting a plan recomputes `fingerprint` per sub-plan; the fingerprint feeds artifact dependency fingerprints. Any existing SDTM/ADaM artifact built from the pre-split aggregate plan therefore no longer matches a current per-domain plan fingerprint. The migration **does not delete** artifacts (immutability), but it marks owner evidence stale by setting the owner's existing `sdtm_derivation_plan_json`/program/XPT-adjacent build evidence to require rebuild via the same `artifacts.mark_owner_stale` semantics the write paths use — concretely, the migration sets affected `ValidationRun`/`ExecutionRun` rows for the aggregate to `stale` and relies on §3.3's per-domain build to regenerate. Stale artifacts are retained for audit; new packages reject them (unchanged packaging rule).
7. `downgrade()` reverses column/constraint additions. Recombining per-domain plans into one legacy DAG is lossy (injected `sdtm_read`/`adam_read` nodes and the ownership choice cannot be unambiguously inverted). **Precise guard (fourth-iteration Finding 5).** After a forward migration plus normal authoring, an aggregate legitimately holds many plan rows — one or more per domain, plus a revision history per domain — so "more than one plan row per `aggregate_id`" is **not** the right split-detection predicate (it would also fire for a single-domain aggregate that merely accumulated two revisions). The guard is instead stated on **distinct natural keys**: downgrade **raises** if any `aggregate_id` has plan rows spanning **more than one distinct `domain_code`** (SDTM) / `dataset_code` (ADaM), **or** if any plan row carries injected `sdtm_read`/`adam_read` pins (i.e. `upstream_plan_pins` is non-empty or the payload contains a `sdtm_read`/`adam_read` node). The only safely-reversible case is therefore an aggregate whose rows all share a single `domain_code`/`dataset_code` (a never-split, single-domain aggregate — possibly with multiple revisions of that one domain) and carry no injected read pins; in that case downgrade drops the new constraints/columns and restores the old unique constraint. Otherwise it raises. This is an intentionally guarded one-way-forward migration; the forward path is the supported one.

Backfill edge cases: (a) a legacy row with no `domain_write` cannot occur under existing coverage enforcement, but if encountered the migration **aborts with context** (fatal, logged) rather than silently producing zero rows; (b) a shared `raw_read` feeding several single-consumer sub-DAGs is duplicated per sub-plan with its id preserved (per-plan id uniqueness holds); (c) a shared `derive`/transform feeding `domain_write`s of multiple domains is resolved by the lexicographic ownership rule in step 2, which is total and deterministic (there is always a unique smallest code).

## 3. API routes, concurrency, and build decomposition

### 3.1 SDTM route changes (`docs/api-contract.md §9.3`, route inventory) + concurrency model (Finding 9)

Single-plan routes are replaced by domain-scoped routes:

```text
GET  /api/v1/sdtms/{sdtm_id}/domains/{domain_code}/derivation-plan
PUT  /api/v1/sdtms/{sdtm_id}/domains/{domain_code}/derivation-plan
POST /api/v1/sdtms/{sdtm_id}/domains/{domain_code}/derivation-plan/validate
POST /api/v1/sdtms/{sdtm_id}/domains/{domain_code}/derivation-plan/preview
GET  /api/v1/sdtms/{sdtm_id}/derivation-plans            # cursor-paginated list of per-domain plan heads
POST /api/v1/sdtms/{sdtm_id}/domains/{domain_code}/validate   # per-domain validation run (authoring/program builds)
GET  /api/v1/sdtms/{sdtm_id}/lineage                     # same path, NEW response shape: domain-keyed lineage map (§3.3)
```

- `{domain_code}` is validated against the pattern and must exist in the current Specification revision (else `404 sdtm_domain_unknown`). The path `domain_code` must equal the body `domain` (else `422 sdtm_plan_domain_mismatch`).
- `GET .../derivation-plans` is a new cursor-paginated collection (opaque cursor via `common/pagination.paginate`, filter-bound by `aggregate_id`) returning each domain's head plan summary. The records paged are the **actual `SdtmDerivationPlanRevision` head rows** — one per `domain_code`, each the max-revision row for its `(aggregate_id, domain_code)` pair — not a synthetic projection; they already satisfy the `CursorRecord` protocol (`id: UUID`, `created_at: datetime`), so `paginate`'s strict newest-first `(created_at, id)` order applies directly with `id` tie-breaking two domain heads that share a `created_at`. The summary projection (`domain_code, revision, alignment_state, alignment_reasons, fingerprint`) is derived from each head row **after** paging, so the cursor key is always the stable row identity and no domain head can be skipped or repeated. See §3.4 `list_plan_heads` for the record source.
- Status codes preserved: `409` for alignment/stale/lifecycle (`sdtm_plan_alignment`, new `sdtm_plan_upstream_misaligned`), `422` for invalid clinical/standards content (coverage, unknown domain write, unresolved/self read, cycle), `problem+json` throughout, idempotency keys unchanged where already required.

**Concurrency model (full specification).** Today every SDTM write (input, spec, plan) matches/bumps/returns the single shared `workbench.revision`. Per-domain plans require independent concurrency tokens so edits to different domains do not collide. The new model:

- **Plan GET/PUT** use `etag_for_revision(domain_plan.revision)` — the per-`(aggregate, domain)` plan revision — as both the `ETag` response header and the `If-Match` token. The first write to a domain that has no plan yet accepts `If-Match` absent or `*` (the existing "no plan yet" path); any concrete `If-Match` on a first write is a mismatch → `412`/`409` via the existing helper.
- **Plan writes stop touching `workbench.revision`.** `put_plan` no longer bumps or consumes `workbench.revision`; its concurrency is entirely per-domain. This removes the divergence the review flagged (a spec/input write bumping the workbench revision while the plan ETag is the domain revision).
- **Spec/input writes keep `workbench.revision`** as their own concurrency token (unchanged) because the Specification and input selection remain single aggregate resources. A spec/input write does **not** change any per-domain plan ETag; instead it misaligns every per-domain plan (§3.4 / Finding 2), and clients learn of the resulting staleness through the plan's `alignment_state=alignment_required` + `alignment_reasons`, **not** through the plan ETag. A GET on a domain plan after a spec change returns the same `revision`/ETag but `alignment_state=alignment_required`; the client must re-save (producing a new plan revision and a new ETag) to realign.

This cleanly separates two concerns: the plan ETag guards concurrent _edits to that plan_, while `alignment_state` guards _staleness from upstream changes_ (spec, input, sibling plan).

### 3.3 Compile / validate / build / execute decomposition (Finding 3)

The build path is single-plan in the verified source (`build_artifact_payload` → one `require_aligned` → one `lower_plan` → one `ValidationRun` keyed by a single `plan_revision`; compile/artifacts/execute take no `domain_code`). The per-domain decomposition is specified end-to-end:

- **Two validation surfaces, reconciled (third-iteration Finding 9).** The verified source has two: the plan-only `POST /sdtms/{id}/derivation-plan/validate` (`validate_plan`) and the aggregate `POST /sdtms/{id}/validate` (`validate_sdtm`), the latter writing one `owner_type="sdtm_workbench"` `ValidationRun` whose `input_manifest` carries scalar `sdtm_revision`/`specification_revision`/`plan_revision`/`plan_fingerprint`/`input_selection_revision`, consumed by aCRF, Define, cSDRG, **and the ADaM input-selection binding** (adam/routes.py ~L269). Making this run per-domain would break every all-domain consumer. The decision: **keep `validate_sdtm` an aggregate validation**, but make its manifest describe the per-domain plan set instead of a single plan.
  - `POST /sdtms/{id}/validate` (aggregate, unchanged path) resolves `plans = aligned_domain_plans(...)` (fail-fast `409` naming the first misaligned domain), lowers **every** per-domain plan, and writes one aggregate `ValidationRun` whose `input_manifest` replaces the scalar `plan_revision`/`plan_fingerprint` with:
    - `plan_revisions`: a sorted map `{domain_code: revision}` over all produced domains;
    - `plan_set_fingerprint`: the ordered hash of per-domain plan fingerprints (a single scalar that changes iff any domain's plan changes).
      It keeps `sdtm_revision`, `specification_revision`, `input_selection_revision`, and the per-domain `normalized_ir` (now a `{domain_code: canonical_ir}` map).
  - A new domain-scoped `POST /sdtms/{id}/domains/{domain_code}/validate` writes a per-domain `ValidationRun` (`input_manifest` with `domain_code`, `plan_revision`, `plan_fingerprint`) for interactive single-domain validation. This exists for authoring feedback and per-domain program builds; it does **not** replace the aggregate run that all-domain deliverables consume.
- **Per-domain build.** `build_artifact_payload(session, aggregate_id, study_id, artifact_type, *, domain_code)` gains a required `domain_code` for per-domain artifacts (XPT, programs). It calls `require_domain_aligned(session, aggregate_id, domain_code)` (validating that domain's spec/input alignment **and** its `upstream_plan_pins`, §6), lowers only that domain's plan, and looks up the per-domain validation run whose `input_manifest["domain_code"] == domain_code` and `input_manifest["plan_revision"] == domain_plan.revision`. `source_plan_revision` on per-domain artifacts is that domain's plan revision.
- **All-domain artifact build (aCRF/Define/cSDRG).** These keep matching the **aggregate** `ValidationRun` but on the new manifest shape: instead of `manifest["plan_revision"] == plan.revision`, they assert `manifest["plan_revisions"] == {D: aligned_domain_plans(...)[D].revision for D}` (equivalently, compare `manifest["plan_set_fingerprint"]` to the freshly recomputed set fingerprint). `build_artifact_payload`'s validation-match description in §9/artifact-catalog is updated accordingly. This is the single place the "all domains validated together" guarantee is enforced for study-level deliverables.
- **Program-artifact multiplicity (decided).** `sdtm_program_python/r/sas` become **per-domain** artifacts: one program set per domain, because each domain's plan lowers to its own IR and independent per-domain alignment means a domain must be buildable without its siblings being aligned. The XPT artifact already identifies its domain via its manifest `dataset`; programs now likewise carry `manifest.domain_code`. `source_plan_revision` on all per-domain SDTM artifacts is the per-domain revision. `artifact-catalog.md §7` is updated for this multiplicity (§9).
- **"Build the whole SDTM output set"** is an orchestration (in the artifact-build worker path) that loops the per-domain plans returned by `aligned_domain_plans` (§3.4) and fails fast with `409 sdtm_plan_misaligned`/`sdtm_plan_upstream_misaligned` naming the first misaligned domain. Packaging selects per-domain XPTs exactly as today, now additionally asserting every produced domain is aligned.
- **Execution** (`/execute`) gains `domain_code`; the execution manifest records the resolved upstream artifacts for any `sdtm_read` (§6 step 4) so provenance stays reproducible.

- **All-domain gate (`aligned_domain_plans`) for study-level deliverables (third-iteration Finding 5).** Define-XML and cSDRG are study/all-domain deliverables: `_build_define_xml_payload` (service.py ~L686) and `_build_csdrg_payload` (~L804) today call `require_aligned(aggregate_id)`. With `require_aligned` gone, both call `aligned_domain_plans(session, aggregate_id)`, which **requires every produced domain to be aligned with satisfied upstream pins** and raises `409 sdtm_plan_misaligned`/`sdtm_plan_upstream_misaligned` naming the first offending domain before any Define/cSDRG bytes are built. `aligned_domain_plans` returns `{domain_code: head_plan}`; the Define reconciliation (which already iterates the selected XPT datasets) and cSDRG section generation iterate that map instead of the single plan. Both builders are added to the §7 `service.py` touch-point list. The Specification itself (the all-domains aggregate) is still read as one record for the Define metadata skeleton; only the plan-alignment gate changes from single-plan to all-domain. The analogous ADaM all-dataset deliverable (ADRG, `_build_adrg_payload`) uses `aligned_dataset_plans` the same way; it is likewise added to §7.

- **`GET /sdtms/{sdtm_id}/lineage` rewrite (third-iteration Finding 3).** Today `get_lineage` does `spec, _, plan = require_aligned(...)`; `internal = lower_plan(spec, plan)`; `return {ir_fingerprint, outputs: lineage(internal)}` over the single aggregate DAG. The rewrite: resolve `plans = aligned_domain_plans(session, sdtm_id)` (fail `409` naming the first misaligned domain — `/lineage` is **all-domain, fail-fast**, matching the build gate, not best-effort, so a partial lineage is never returned); for each domain lower its plan to IR and compute per-domain `lineage(ir)`. The response is a **domain-keyed map** `{"domains": {domain_code: {"ir_fingerprint": ..., "outputs": lineage(ir)}}}` plus a top-level `plan_set_fingerprint` (the ordered hash of per-domain `ir_fingerprint`s) for a stable whole-set identity. A cross-domain `sdtm_read{dataset=B}` lowers to an IR `ReadNode{dataset=B}` whose `dataset` names B's produced output; its lineage entry therefore references `B` by code, and the client stitches cross-domain lineage by following that reference into the `B` entry of the same map (the server does not merge the per-domain IRs into one graph — each IR stays domain-scoped, and the `sdtm_read` is the explicit, pinned cross-domain edge). This is a **response-shape change** from the current flat `{ir_fingerprint, outputs}`; it is recorded in the §9 api-contract edit and covered by a contract test (§10). ADaM `GET /adams/{adam_id}/lineage` is rewritten symmetrically over `aligned_dataset_plans` with the same map shape.
- ADaM mirrors all of the above per dataset (`validate_adam`, `build_artifact_payload(..., dataset_code=...)`, per-dataset `adam_program_*`).

OpenAPI is a versioned contract: regenerate the typed-client fixture; update contract tests for the new paths, the new `alignment_reasons` value `upstream_plan_changed`, and the `409 sdtm_plan_upstream_misaligned`/`adam_plan_upstream_misaligned` problem codes. The plan resource is intentionally repathed (a documented versioned change recorded in §9).

### 3.4 New/changed service functions (Finding 1, 2, 3)

SDTM `service.py`:

- `latest_plan(session, aggregate_id, domain_code)` — max-revision for the pair.
- `list_plan_heads(session, aggregate_id) -> tuple[SdtmDerivationPlanRevision, ...]` — returns the actual head `SdtmDerivationPlanRevision` rows (the max-revision row per `domain_code`, one per domain), ordered newest-first by `(created_at, id)`. - `aligned_domain_plans(session, aggregate_id) -> dict[str, SdtmDerivationPlanRevision]` — the **all-domain gate**: latest plan per domain, requiring every domain that has a plan to be `aligned` with satisfied pins, raising `409 sdtm_plan_misaligned`/`sdtm_plan_upstream_misaligned` naming the first offending domain. - `specification_slice(specification, code)` (§5).
- `mark_sibling_plan_change(...)` and the rewritten refresh paths (below).

Output shape (corrected — the prior design wrongly asserted no consumer reads the scalar). ## 4. SDTM read node authoring contract, IR lowering, and output coverage (Finding 6)

Authoring rules (enforced in `lower_plan`, module-owned, not in `common`):

1. `sdtm_read.dataset` must be a domain declared in the aligned Specification revision **and must not equal this plan's own `domain`** (self-reads use `raw_read`). Violations → `422 sdtm_read_target_unknown` / `422 sdtm_read_self`.
2. The read resolves to the upstream domain's expected output structure from the Specification sub-slice (`SdtmDomain.variables`), so downstream nodes reference its columns without a separate pinned SDTM input selection. The Raw `input_selection_revision` remains the only external input pin.
3. **Lowering:** `sdtm_read → DataflowIR ReadNode{dataset=<domain code>}`. The IR `read` already means "read a named dataset." The compiler resolves a `read` whose dataset name matches a Specification domain code to that domain's produced XPT (pinned via `upstream_plan_pins`, §6); a `read` whose name matches a Raw dataset code resolves to the Raw input selection. The compiler distinguishes by membership in the Specification domain set. **No `transformation/` contract change**; a lowering/compiler comment documents the dual meaning of a `read` dataset name. Raw Python/R/SAS/SQL/arbitrary expression strings remain invalid in authoring models (unchanged).

**Per-domain output coverage invariant (precise).** For a plan whose `domain = D` with Specification slice `spec_slice`:

- **Exactly one `domain_write`, and its `domain == D`.** More than one `domain_write` → new `422 sdtm_plan_output_duplicate`. A `domain_write` whose `domain != D` → new `422 sdtm_plan_output_scope`. This replaces today's subset check with an exact per-domain check (today SDTM has no "one write per domain" rule; ADaM already enforces one via `adam_plan_output_duplicate`).
- **`D` is required iff `D` has any derived variable:** `required = {D} if any(var.derived for var in spec_slice.target.variables) else {}`; `writes = {node.domain}`; raise `sdtm_plan_output_coverage_missing` when `required - writes` is non-empty (now reduces to "a derived domain must declare its one write").
- **Variable-level single producer (decided, scoped):** SDTM does **not** gain an `output_node_id` variable→node coverage rule in this change. ADaM already keys each variable to its producing node via `output_node_id`; SDTM's authoring model has no such field and adding it is out of scope here (it is the same deferred "exactly one producing output" envelope item as Finding 5). The per-domain invariant SDTM enforces is dataset-level (exactly one `domain_write` of `D`), which is what per-domain separation requires. §9 states this explicitly so §4.7's "exactly one valid producing output" wording is reconciled to the dataset-level rule SDTM actually enforces, with the variable-level rule deferred.
- **SDTM invariant is dataset-level, stated precisely (third-iteration Finding 2).** The per-plan rule SDTM enforces is exactly: _exactly one `domain_write` whose `domain == D`, and `D` must have such a write iff `D` has any derived variable._ This is a **dataset-level** single-producer rule. SDTM does **not** enforce a variable-level "every derived variable has exactly one producing node" rule — it has no `output_node_id` field and adding one is deferred (same deferral as Finding 5). The §9 §4.7 rewrite must therefore state the SDTM invariant as _dataset-level_ and must not reuse §4.7's current phrase "exactly one valid producing output" without qualifying it to the dataset write; the variable-level rule remains an ADaM-only mechanism (`output_node_id`) in Release 1.

- **Collective whole-Specification coverage, with the never-authored-domain case made explicit (third-iteration Finding 2).** No single request sees all plans, so the union invariant — `⋃ over domain plans {written domain} == {domains with any derived variable}` — is checked in the **build/packaging orchestration** (§3.3), not in `lower_plan`. The orchestration computes `derived_domains = {D in spec : D has a derived variable}` directly from the Specification revision (not from the plan set), and `covered = {p.domain_code for p in aligned_domain_plans(...)}`. A derived domain for which the user **never authored a plan row** contributes nothing to `covered` and therefore appears in `derived_domains - covered`; the build fails with `409 sdtm_output_coverage_incomplete {missing_domains}` naming it. This is intentional and is the behavior Finding 2 asks to confirm: `aligned_domain_plans` returns only domains that have a plan and requires each such plan to be aligned, so it does **not** mask a never-authored derived domain — the missing-set is computed against the Specification's `derived_domains`, not against the keys of `aligned_domain_plans`. (A separate failure, a plan that exists but is misaligned, surfaces earlier as `409 sdtm_plan_misaligned` from `aligned_domain_plans` itself; the coverage check only runs once every existing plan is aligned.) This is the only place the full set is visible. The ADaM collective check is symmetric over `aligned_dataset_plans`.

### 4.1 ADaM cross-dataset read equivalent (Finding 3, 6)

ADaM already has `sdtm_read` (reads selected SDTM XPT, pinned by the ADaM input selection — unchanged) and `adam_read` (reads a predecessor ADaM dataset). Today `_validate_dataset_dependencies` requires each `adam_read` to be fed by an **in-plan** `dataset_write`. With per-dataset plans that in-plan write no longer exists, so the rule changes:

- `adam_read.dataset` must be a dataset declared in the aligned Specification and **must not equal this plan's own `dataset`**. It resolves to that predecessor dataset's declared variables from the Specification sub-slice (exactly as `source_kind="adam"` predecessor origins already resolve in `validate_origins`). Unknown/self → `422 adam_read_target_unknown` / `adam_read_self`.
- Lowering stays `adam_read → select(predecessor dataset variables)`; the compiler resolves the predecessor dataset name to that dataset's produced XPT, pinned via `upstream_plan_pins` (§6).
- The in-plan `adam_plan_predecessor_output_missing`/`adam_plan_predecessor_edge_missing` checks are **removed** (there is no in-plan write for a cross-dataset read anymore). The acyclicity check that `_validate_dataset_dependencies` performed inside one plan moves to a **cross-plan** check at write time: the set of predecessor datasets a plan reads, resolved transitively through each sibling plan's `upstream_plan_pins`, must not form a cycle across the aggregate's per-dataset plans. `adam_plan_dataset_cycle` is retained but evaluated across plans using pins.

Because §6 step 2's write-time gate forbids pinning a sibling that is not already `aligned`, a true cross-plan cycle can never be committed: in a 2-cycle (A reads B, B reads A) the second member to be written could never find its counterpart already aligned, so it cannot commit a pin. `adam_plan_dataset_cycle` therefore fires at **write time** (inside `put_plan`, before commit), traversing the directed graph formed by this plan's `adam_read` targets plus the transitive closure of the current `upstream_plan_pins` of its already-aligned siblings; it is primarily a defensive check against a pin set that became cyclic through concurrent sibling writes. The SDTM side is symmetric: `sdtm_read` targets can likewise form a cross-plan cycle, so SDTM evaluates the identical write-time closure check and raises `422 sdtm_plan_dataset_cycle` under the same gate guarantee.

- ADaM per-dataset output coverage: exactly one `dataset_write` of this plan's `dataset` (existing `adam_plan_output_duplicate`), plus `output_node_id` lineage resolving within this plan's nodes for that dataset's variables only (existing `adam_plan_variable_lineage_missing`, now scoped to the dataset's own variables). The collective coverage union is checked in ADaM's build/packaging orchestration exactly as SDTM's.

## 5. Specification sub-slice resolution

The Specification stays one aggregate. A per-domain/per-dataset plan is validated against a **sub-slice** of the aligned Specification revision:

- SDTM: `spec_slice = specification_slice(specification, plan.domain)` returns `{target: SdtmDomain, siblings: {code: variables}}` — the owned target domain plus a read-only view of sibling domains' `{code, variables}` needed to type-check `sdtm_read` targets. `lower_plan` restricts coverage, `domain_write`, and `derive.target_domain` to `plan.domain`, while allowing `sdtm_read` to reference any other declared domain. No persistence split of the Specification occurs.
- ADaM: identical, with `dataset` in place of `domain` and `adam_read` referencing other declared datasets.

`specification_slice(specification, code)` lives in each module's `service.py` (module-owned; not in `common` — it encodes clinical ownership semantics).

## 6. Cross-domain / cross-dataset staleness correctness gap (decision 4) — RESOLVED

**The gap is real.** Under the approved "Specification-only binding, no new SDTM input pin" rule: domain A's plan reads domain B's output via `sdtm_read`. The only pins A carries are `specification_revision` and the Raw `input_selection_revision`. If B's **plan** changes (new `domain_write` logic) while the Specification and Raw selection are untouched, A's alignment state does not change — A still points at the same Specification revision — yet A's compiled/executed output is now based on a stale understanding of B. A would silently execute against an outdated B. The same holds for ADaM: dataset A2 reading predecessor dataset B2 via `adam_read` would not notice B2's plan revision changing.

The Specification-only model **cannot** close this, because the thing that changed (B's plan) is not the Specification and is not an external input selection. Pinning only the Specification is insufficient whenever cross-plan reads exist. Hand-waving ("the user will re-run everything") violates the platform's staleness guarantees and the "block compilation/execution until aligned" rule.

**Minimal mechanism (adopted): server-resolved upstream-plan pins + an `upstream_plan_changed` staleness edge.** This preserves decision 4's letter (no new _external_ input-selection revision; the Raw/SDTM input selection stays the only external pin; cross-domain binding still resolves _structurally_ through the Specification) while adding an _internal, same-aggregate_ dependency pin:

1. **At plan write time (`PUT`)**, within the single write transaction, the service computes `upstream_plan_pins` from the plan's `sdtm_read`/`adam_read` nodes: for each referenced sibling domain/dataset it looks up that sibling plan's **current latest revision** in the same aggregate and records `{code, plan_revision}` (sorted, de-duplicated). These pins are server-resolved, never client-supplied, so no external input-selection pin is added to the authoring envelope. The pin read and the reader-plan insert happen in the same transaction/commit.

2. **Write-time sibling-alignment gate (Finding 4).** A pin whose referenced sibling plan is **not currently `aligned` against the same `specification_revision`** is **rejected at `PUT`** with `409 sdtm_plan_upstream_misaligned` (ADaM: `409 adam_plan_upstream_misaligned`), carrying `{domain/dataset, upstream_code, upstream_state}`. This forbids creating a plan born blocked and makes the remediation order explicit: **upstream domains/datasets must be aligned first**. A reader cannot be saved until the sibling it reads is itself aligned against the reader's target Specification revision. This closes the ordering/consistency hole the review flagged — there is no "pin a misaligned sibling" state.

   **Never-authored sibling (fourth-iteration Finding 1).** A referenced sibling may be declared in the Specification yet have **no plan row at all** (never authored). This is a distinct state from "misaligned": there is no revision to pin and no `state` to check, so §4 rule 1's Specification-membership check does not catch it. The §4 authoring validation only confirms `sdtm_read.dataset`/`adam_read.dataset` is a domain/dataset declared in the aligned Specification revision; it does **not** confirm a plan row exists. Pin resolution therefore adds an explicit existence check: at `PUT`, if a referenced sibling has **no plan row**, the write is **rejected** with `409 sdtm_plan_upstream_misaligned` (ADaM: `409 adam_plan_upstream_misaligned`), carrying `{domain/dataset, upstream_code, upstream_state: "absent"}` — reusing the existing upstream-misaligned code because the remediation is identical: **author/align the upstream domain/dataset first**. This closes the silent-no-pin correctness hole (A must never compile against a non-existent B — the exact gap Decision 4 exists to close) by making "sibling has no plan" a first-class rejected state alongside "sibling misaligned." The two upstream states are distinguished by the `upstream_state` field: `"absent"` (no plan row) vs the misaligned/stale states carried by the step-4 check.

3. **Transitive misalignment propagation (third-iteration Finding 1).** `mark_sibling_plan_change(session, aggregate_id, changed_code, reason)` is the single primitive every misalignment path calls. It is **not** gated on "a new revision was created"; it fires on **any transition of a plan into `misaligned`**, including when a plan becomes misaligned because of a spec change, an input change, or — critically — because one of _its own_ upstream pins became stale. Its body:
   - Find every sibling plan head in the aggregate whose `upstream_plan_pins` reference `changed_code`.
   - For each such head still in `state="aligned"`, set `state="misaligned"` and append reason `upstream_plan_changed` (idempotent: a head already misaligned for that reason is untouched, which is also the recursion's termination condition).
   - For each head it _newly_ flipped to misaligned, **recurse**: call `mark_sibling_plan_change(session, aggregate_id, that_head.domain_code, "upstream_plan_changed")`, so staleness walks the entire pin DAG in the same transaction.

   **Termination argument.** The pin graph within an aggregate is a DAG — §6 step 2's gate forbids pinning a sibling unless it is already `aligned`, and §4.1's write-time closure check (`sdtm_plan_dataset_cycle`/`adam_plan_dataset_cycle`) rejects any write whose pins would close a cycle. Propagation only ever flips an `aligned` head to `misaligned` and never revisits a head already misaligned-for-this-reason, so each node transitions at most once; on a finite acyclic graph the recursion terminates. Every entry point that creates a new revision of B (B's own `put_plan`), and every entry point that misaligns B for a spec/input reason (§3.4's five refresh sites), ends by calling `mark_sibling_plan_change(..., B.domain_code, ...)` so B's downstream readers are flipped in the **same commit**. There is therefore no committed state in which A reports `state=aligned`/`reasons=[]` while an upstream it transitively depends on is misaligned — restoring the §2.3 iff invariant.

4. **`require_domain_aligned`/`require_dataset_aligned`** are now a cheap consistency check rather than the propagation mechanism (propagation already happened eagerly in step 3). For the requested domain plan they verify: (a) its own `state == "aligned"` and `spec/input` revisions current; and (b) for each pin, that the referenced sibling head still exists at the exact pinned `plan_revision` and is itself `aligned`. A failure of (a) returns `409 sdtm_plan_misaligned` with the plan's own `alignment_reasons`; a failure of (b) returns `409 sdtm_plan_upstream_misaligned` with `{domain, upstream_code, pinned_revision, current_revision}`. Both the self-misaligned and upstream-stale cases are already reflected in the persisted `state`/`alignment_reasons` by step 3, so `GET` and `require_*` agree — the client is never told `current` while an operation would `409`. Compile/preview/validation/execution/packaging all go through `require_*`. **Execution manifests** record the resolved upstream artifact (the exact XPT of the pinned upstream plan revision), so a `read` of an SDTM domain / predecessor ADaM dataset resolves to that domain's/dataset's XPT produced by the pinned plan revision — provenance stays reproducible.

**Isolation note (third-iteration Finding 6).** The plan tables are **append-only** — a new revision is a new `INSERT`, not an `UPDATE` of the head row — so a `SELECT ... FOR UPDATE` on "the sibling's current max-revision row" does **not** prevent a concurrent transaction from `INSERT`ing a higher revision (no gap lock under READ COMMITTED). The prior design's sibling-head row lock was therefore unsound and is replaced. The adopted mechanism: **any plan write in an aggregate first acquires a row lock on the parent aggregate row** — `SELECT ... FROM sdtm_workbenches WHERE id = :aggregate_id FOR UPDATE` (ADaM: `adam_workbenches`) — at the top of `put_plan`, before resolving pins or inserting the new revision. This serializes _all_ plan writes within one aggregate (including sibling writes), so the interleave "A pins B@3 while B commits B@4" cannot occur: whichever write holds the aggregate lock runs to commit (resolving pins and running `mark_sibling_plan_change`) before the other begins. Contention is negligible — plan writes are low-frequency authoring actions, and the lock is held only for the duration of a single plan write, not across I/O. The workbench row already exists for every aggregate (`sdtm_workbenches`/`adam_workbenches`, verified), so no schema change is needed. This is the one place the design relies on row locking; the lock **target** is the aggregate row and the isolation level is the platform default READ COMMITTED (the aggregate lock, not isolation, provides serialization). `put_plan` holds no object-store or runner I/O inside this lock (AGENTS.md "do not hold a transaction open while rendering/accessing storage/running programs").

**Sibling-domain removal from the Specification (third-iteration Finding 11).** Pins reference sibling plan rows via a `{domain_code, plan_revision}` JSONB entry with no FK; revisions are immutable and retained, so a pinned revision always exists physically. The only way a pin can dangle is if the sibling **domain is dropped from the Specification entirely**. That is a Specification change: it misaligns **every** per-domain plan (reason `specification_changed`, §3.4), including A, so A cannot operate until re-saved. On A's re-save against the new Specification revision, A's `sdtm_read{dataset=B}` now fails `422 sdtm_read_target_unknown` (B is no longer a declared domain), forcing the author to remove the dangling read before A can realign. There is thus no committed state where A keeps a live pin to a dropped domain. (ADaM `adam_read` to a dropped dataset is symmetric: `422 adam_read_target_unknown`.)

This mechanism is strictly additive: the external input pin is unchanged, cross-domain _structure_ still comes from the single Specification, and the new pin is an internal same-study/same-aggregate plan-revision reference the system resolves and maintains automatically. Cross-aggregate reads are out of scope (a domain plan reads only sibling domains in its own SDTM workbench; an ADaM dataset reads only sibling datasets in its own ADaM workbench), so pins never cross a study boundary.

Why not a lighter option: (a) pinning nothing and re-deriving staleness from fingerprints at build time would let a stale A compile against an old cached B and only fail at packaging — too late, and it violates "block compilation until aligned"; (b) a single aggregate-wide "any plan changed" flag would over-stale unrelated domains, breaking the per-domain independence the user asked for. The per-read pin with the write-time gate is the minimal correct option.

- Per-domain **exact** coverage: `sdtm_plan_output_scope` (write of wrong domain), `sdtm_plan_output_duplicate` (>1 write), `sdtm_plan_output_coverage_missing` (derived domain with no write), and acceptance of a non-derived domain's plan with zero writes.
- Lowering of `sdtm_read → read` and `domain_write → write` restricted to the plan's domain; `specification_slice` returns the owned target plus sibling variable map.
- ADaM: `adam_read` cross-dataset resolution against the Specification sub-slice; removal of the in-plan predecessor-edge requirement; cross-plan cycle detection via pins; per-dataset coverage and `output_node_id` lineage scoped to the dataset.
- Envelope: `schema_version` is `Literal["1.1.0"]`; `domain`/`dataset` required; response `alignment_state`/`alignment_reasons` mapping including `upstream_plan_changed`.
- Staleness unit: writing B's plan marks A (which pins B) `misaligned` reason `upstream_plan_changed`; a `PUT` pinning a non-aligned sibling raises `409`; `require_domain_aligned` raises `409` when a sibling advanced past the pin.
- **Never-authored sibling (fourth-iteration Finding 1):** a `PUT` whose `sdtm_read.dataset`/`adam_read.dataset` names a Specification-declared sibling that has **no plan row** is rejected with `409 sdtm_plan_upstream_misaligned`/`adam_plan_upstream_misaligned` carrying `upstream_state: "absent"` (distinct from the "sibling misaligned" case); after the sibling is authored and aligned, the same `PUT` succeeds and records the pin.
- **Transitive staleness (third-iteration Finding 1):** chain A pins B, B pins C; a new revision of C flips B→`misaligned`, and the propagation recurses to flip A→`misaligned` reason `upstream_plan_changed` in the **same transaction**; afterwards `GET A` reports `alignment_state=alignment_required` (never `current` while an operation `409`s), and the §2.3 iff holds across the whole chain. A separate test asserts termination on a diamond (A pins B and C; B and C both pin D).
- Migration split helper (pure dict→dict): single-DAG → per-domain sub-plans; lexicographic ownership of a node feeding two writes; injected `sdtm_read` + pin on the non-owner; preserved node ids; `node_id → domain_code` map correctness.

Property:

- `domain_code`/`dataset_code` pattern; graph DAG/ports/edges for plans containing `sdtm_read`/`adam_read`; `upstream_plan_pins` canonical ordering/dedup; migration split determinism over randomized legacy DAGs (same input → same per-domain partition and ownership).

Repository integration (migrations applied from an empty DB, not `metadata.create_all`):

- Per-`(aggregate, domain)` / per-`(aggregate, dataset)` uniqueness; revision counter per domain/dataset; `upstream_plan_pins`/`alignment_reasons` JSONB round-trip.
- Spec/input/refresh marks **every** domain/dataset plan `misaligned` with the correct reason (covers all five call sites — Finding 2).

- **aCRF plan-node resolution (third-iteration Finding 4):** with per-domain revisions sharing numbers across domains, `sdtm/acrf.py` link validation and coverage resolve by `(aggregate_id, domain_code, revision)`; a legacy `AcrfPlanNodeLink` with a null `domain` after backfill is reported as unresolved (`acrf_plan_node_unresolved`) rather than silently matching the wrong domain's plan.
