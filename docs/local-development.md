# Local Development

## 1. Target local stack

Local development uses Python 3.13 and Docker Compose. The completed Phase 1 Compose
stack provides:

- PostgreSQL 16;
- MinIO and a bootstrap process for the development bucket;
- FastAPI application;
- durable job worker for builds, validation, reconciliation, and packaging;
- execution dispatcher;
- signed-event integration dispatcher and bounded local test receiver;
- isolated Python runner image;
- isolated R runner image.

SAS is optional and external. Without a configured adapter, SAS compilation works and SAS execution returns `runner_not_configured`.

The foundation runs the API, migrations and catalog seed, build and integration workers,
PostgreSQL, MinIO, and the development-only webhook receiver through Compose. Python and
R runner images are isolated Compose profiles; clinical compilation and execution handlers
are introduced in later delivery phases.

## 2. Prerequisites

- Git
- Python 3.13
- Docker Engine with Compose v2
- At least 8 GB of memory available to Docker for the full stack

Use a project-local virtual environment. Do not install Python or R runner dependencies globally; their authoritative environments are the runner images.

## 3. Initial setup

From the repository root:

```powershell
Copy-Item .env.example .env
uv sync --extra dev
uv run alembic heads
uv run uvicorn app.main:app --reload
```

Once the Phase 1 container assets are present, bring up the service-backed development
environment with:

```powershell
docker compose build
docker compose up -d postgres minio minio-init
uv run alembic upgrade head
uv run python -m app.catalog_seed
```

Start the API and workers either in Compose or as local Python processes. For a consistent integration environment:

```powershell
docker compose up -d api build-worker integration-receiver integration-dispatcher
```

For faster API iteration:

```powershell
uvicorn app.main:app --app-dir src --reload
```

Run workers through their declared package entry points in `pyproject.toml`; those entry points should call the same worker code used by the container images.

## 5. Database workflow

Create migrations from deliberate model changes:

```powershell
alembic revision --autogenerate -m "describe the change"
alembic upgrade head
```

Review autogenerated migrations before committing them. In particular, verify enum changes, JSONB defaults, partial indexes, uniqueness scope, foreign-key delete behavior, and concurrent/index operations.

Useful local operations:

```powershell
alembic current
alembic history
docker compose exec postgres psql -U clinical -d clinical
```

Tests create isolated databases or schemas and apply migrations from zero. They must not depend on a developer's current database state.

## 6. Object storage workflow

MinIO's API endpoint is configured through `OBJECT_STORE_ENDPOINT`. The bootstrap service creates the development bucket and applies no public-read policy. Use the MinIO console only for diagnosis; normal workflows must upload and download through application APIs.

Object keys are checksum-addressed and generated by the artifact service. Never construct keys from study names, user filenames, domain codes, or archive paths. Development fixtures should use the same storage abstraction as production.

## 7. Authentication in development

Compose includes a development-only `test-issuer`. It generates an ephemeral RSA key at each start, publishes its public JWKS, and issues tokens lasting no more than one hour. Its port binds only to host loopback. A restart invalidates previously issued tokens because no private key is persisted.

Start the API and issuer, then request a token:

```powershell
docker compose up -d --build api

$tokenResponse = Invoke-RestMethod `
  -Method Post `
  -Uri "http://127.0.0.1:18081/token" `
  -ContentType "application/json" `
  -Body '{"subject":"local-developer","scope":"*","lifetime_seconds":3600}'

$headers = @{ Authorization = "Bearer $($tokenResponse.access_token)" }
Invoke-RestMethod `
  -Uri "http://127.0.0.1:18000/api/v1/standards?provider=CDISC" `
  -Headers $headers
```

The issuer claim contract is `iss=https://local-issuer.example`, `aud=clinical-artifact-platform`, a non-empty `sub`, integer `iat` and `exp`, and a space-delimited string `scope`. The Compose API resolves JWKS through the internal `test-issuer` service name; a host-run API uses `JWT_JWKS_URL=http://127.0.0.1:18081/.well-known/jwks.json`. Override the loopback host port with `DEV_JWT_PORT` when necessary.

For a completely host-run environment, copy `.env.example` to the ignored `.env` file and ensure these values agree:

```text
JWT_ISSUER=https://local-issuer.example
JWT_AUDIENCE=clinical-artifact-platform
JWT_JWKS_URL=http://127.0.0.1:18081/.well-known/jwks.json
JWT_ALGORITHMS=RS256

DEV_JWT_ENABLED=true
DEV_JWT_ISSUER=https://local-issuer.example
DEV_JWT_AUDIENCE=clinical-artifact-platform
```

Both processes load that file when started from the repository root:

```powershell
uv run uvicorn support.dev_jwt_issuer:create_environment_app `
  --factory --host 127.0.0.1 --port 18081 --no-access-log

# Run in a second terminal.
uv run uvicorn app.main:app --host 127.0.0.1 --port 18000
```

The issuer refuses to start unless `DEV_JWT_ENABLED=true`. Do not carry that setting into production configuration. `.env` is ignored by Git and must not contain production credentials.

Do not add an application code path that disables authentication. Automated tests may replace the verifier through dependency injection, while integration and end-to-end tests exercise real signature, issuer, audience, expiry, and study-membership checks.

## 8. API usage

With the service running:

```text
OpenAPI JSON: http://localhost:18000/api/v1/openapi.json
Swagger UI:   http://localhost:18000/docs
Liveness:     http://localhost:18000/health/live
Readiness:    http://localhost:18000/health/ready
```

Compose binds the development API to host loopback only. Override its host port with `API_PORT` when necessary; the container continues to listen on port 8000.

Mutating requests require `Authorization: Bearer <token>`. Direct edits require the current `ETag` in `If-Match`. Bulk imports, artifact builds, executions, reconciliation runs, integration redeliveries, and package requests also require an `Idempotency-Key` header.

## 9. Running tests

Fast feedback:

```powershell
pytest tests/unit
pytest tests/contract
```

Service-backed suites:

```powershell
pytest tests/integration
pytest tests/conformance
```

Full workflow:

```powershell
pytest tests/e2e
```

The Phase 2 Documents PostgreSQL workflow can be run independently after migrations and
catalog seeding:

```powershell
$env:AURINARA_INTEGRATION = "1"
pytest tests/integration/test_phase2_documents.py
```

The seeded `REPORT_LAYOUT` family contains immutable version `2.0.0` for Documents
DOCX/PDF/XLSX artifacts. A formatted Documents build must explicitly select that exact
Template version for every requested formatted artifact type. Protocol and document
content `PUT` operations require `If-Match`; atomic content/USDM imports additionally
require `Idempotency-Key`. Validation snapshots bind the exact document, content, USDM,
evidence, related-document, and dependency revisions used by a build.

Testcontainers may start PostgreSQL and MinIO automatically. If the project supports a Compose test profile, it must offer equivalent versions and settings. Mark resource-intensive execution tests so developers can select them explicitly while CI always runs them at the required stage.

Compose exposes the development-only callback receiver on `http://localhost:8082`; the
dispatcher shares its network namespace so configured callbacks use
`http://127.0.0.1:8080/events`. The receiver captures only bounded event bytes and signing
headers, deduplicates by event ID, supports deterministic failure sequences, and exposes no
general proxy behavior. Only test/development configuration may enable loopback delivery.

Other required checks should be exposed as stable project commands, for example:

```powershell
ruff check .
ruff format --check .
mypy src workers
pytest
```

The exact commands belong in `pyproject.toml` and CI rather than being duplicated in ad hoc scripts.

## 10. Golden and conformance fixtures

Golden fixtures cover normalized XML, DOCX, PDF, RTF, XLSX, and generated program output. Updating a golden file is a reviewed change: record the generator/template/schema version change and inspect rendered output before accepting it.

Compiler fixtures include canonical, revision-aligned SDTM and ADaM Specification/Derivation Plan pairs and TLF ARS/ProgramPlans together with their normalized internal IR, generated Python/R/SAS source, lineage, and normalized expected results. Contract fixtures verify that SDTM and ADaM share envelope fields, endpoint lifecycle, concurrency, and alignment behavior while rejecting each other's module-only content. Dataflow fixtures run through Python and R and compare schema, declared ordering, exact structural/discrete values, missing-value behavior, and assertions. Statistical fixtures use procedure-declared numeric tolerances and pinned algorithm/library versions; they never hide a different method behind a broad tolerance. Boundary fixtures prove that stale Specification or input revisions block plan operations, TLF rendering is absent from IR, raw backend code is rejected, IR is not publicly writable, and unsupported backend capabilities fail before program publication.

Pinned standards assets live under `schemas/`, controlled terminology releases under `terminology/`, and presentation assets under `templates/`. Each asset family has reviewed provenance, version, checksum, license or distribution metadata, and compatibility records loaded by its registry. Tests must run without downloading schemas, terminology, or templates. Define-XML tests cover both 2.0 and 2.1. XPT tests write, read back, and compare the supported metadata and data values.

### Snapshotting and registering CDISC Library

CDISC Library acquisition is an explicit offline administration step, never an API or worker behavior. Set the API key only for the snapshot process, then remove it from the shell:

```powershell
$env:CDISC_LIBRARY_API_KEY = "<key>"
python -m app.cdisc_registry snapshot-all
Remove-Item Env:CDISC_LIBRARY_API_KEY

python -m app.cdisc_registry register-snapshot `
  schemas/cdisc-library/<overall-last-updated>/snapshot-manifest.json
```

The resulting checked resources are repository assets. Review their provenance and applicable CDISC license before committing or distributing them. Re-running registration with the same immutable snapshot is idempotent; changed bytes under an existing identity are rejected.

### Registering approved CDISC packages

CDISC package bytes are not downloaded by application processes. Place approved standard assets and a `CdiscStandardManifest` JSON file below `schemas/`; place each approved Controlled Terminology manifest below `terminology/`. The manifest contracts are defined in `app.standards.contracts` and `app.terminology.contracts`. Register model releases before implementation guides, and standard releases before terminology manifests that reference them:

```powershell
python -m app.cdisc_registry register-manifests `
  --standard-manifest schemas/cdisc/sdtm-1-7/manifest.json `
  --standard-manifest schemas/cdisc/sdtmig-3-3/manifest.json `
  --terminology-manifest terminology/cdisc/sdtmct-2024-09-27.json
```

Registration is atomic. An unsafe path, invalid manifest, missing compatibility target, or checksum mismatch rejects the transaction. Re-running an identical manifest is idempotent; reusing an identity for different bytes is rejected. CDISC Library API keys must not be committed.

Synthetic study fixtures must create explicit dependency selections for Raw, Documents, SDTM, ADaM, and TLF. A fixture identifies exact Standard and Template versions, Terminology releases and extension revisions, and Reference revisions; it must never resolve `latest`. Registry fixtures include compatible and incompatible combinations, deprecated or quarantined versions, and superseded Reference/extension revisions so tests can verify no implicit upgrade, refresh-required state, and transitive staleness. Template fixtures contain presentation and blank structure only—never clinical narrative or decisions.

Keep synthetic clinical fixtures free of real patient information. Raw datasets, PDFs, and expected outputs should be small enough for routine CI while covering non-ASCII text, missing values, long labels, value-level metadata, multiple annotations, and traceability chains.

## 11. Module and integration development

Every core and deployment-added module registers through the same `ModuleDescriptor` and typed capability protocols. A new module change includes:

1. A one-word lowercase module key and unique API prefix.
2. Its domain package, Pydantic contracts, application services, repository, and Alembic migrations.
3. Only the capability implementations it declares, such as dependency selection/staleness, validation, entity resolution, artifacts, traceability, review, reconciliation, packaging, compilation, execution, or events.
4. Stable dependency-purpose, entity, relationship, artifact, source-plan, event, authorization-scope, and schema-version identifiers.
5. Unit tests for descriptor conflicts and capability behavior, contract/OpenAPI tests, migration tests, and a synthetic composition test proving shared services need no module-name branch.

Do not discover modules by scanning the filesystem or loading user-selected import paths. The application composition root imports reviewed module descriptors explicitly. Restarting with a new application build activates a newly included module after its migrations succeed; modules are not hot-installed.

For outbound integration tests, create a study-scoped integration and subscription through the API, retain the one-time signing secret only in test memory, and verify the event ID, timestamp, content digest, and HMAC over the exact request bytes. Exercise success, timeout, bounded error response, retry, dead-letter, redelivery, retirement, secret rotation, and SSRF rejection. Event fixtures contain identifiers and status summaries, never clinical payloads or raw rows.

## 12. Runner development

The dispatcher stages each run in a newly created temporary workspace with separate read-only input and writable output locations. Local runners must preserve production controls:

- run as a non-root user;
- disable external networking;
- mount only the run workspace;
- keep the image filesystem read-only where supported;
- enforce CPU, memory, process, wall-time, and output-size limits;
- capture stdout, stderr, exit code, and metrics;
- validate declared outputs before upload;
- remove the workspace after terminal processing.

Build runner images after changing compiler or runtime dependencies:

```powershell
docker compose build python-runner r-runner
```

Execution tests should include timeout, cancellation, memory pressure, unexpected files, oversized output, nonzero exit, malformed XPT, and attempted network access.

## 13. Worker and job diagnosis

Jobs are claimed with short `FOR UPDATE SKIP LOCKED` transactions and then processed outside database locks. If a worker stops, another worker can reclaim the job after its lease expires.

For diagnosis, inspect structured logs using the request ID, job ID, build ID, validation run ID, reconciliation run ID, execution run ID, artifact ID, review item ID, and study ID. Do not log JWTs, secrets, full clinical payloads, review-comment bodies, or raw dataset rows.

Common checks:

```powershell
docker compose ps
docker compose logs api
docker compose logs build-worker
docker compose logs execution-dispatcher
docker compose logs integration-dispatcher
```

Retry behavior must be tested with idempotent builders and delivery scheduling. A build retry may reuse already uploaded checksum-identical bytes, but it must not create conflicting artifact metadata or execute a completed package command twice. An integration retry creates another attempt for the same immutable event/subscription revision and never republishes the domain event.

## 14. Resetting local services

Stop the stack without deleting state:

```powershell
docker compose down
```

Removing local volumes destroys the development PostgreSQL database and MinIO objects. Use it only when that loss is intended:

```powershell
docker compose down --volumes
```

After a volume reset, start infrastructure, recreate the bucket through `minio-init`, and run `alembic upgrade head` again.

## 15. Definition of a reviewable change

A change is ready for review when module boundaries are preserved, descriptors and capability ownership are conflict-free, migrations upgrade a clean database, OpenAPI and event/import schemas reflect the intended compatible contracts, relevant unit/integration/security/conformance tests pass, generated artifacts have updated golden evidence when needed, and the documentation describes any new setting, module capability, connector, runner dependency, schema/template version, or operational step.
